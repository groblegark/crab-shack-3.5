# CRAB SHACK on iOS

A native shell around the game. **There is no iOS build of the game and there
must never be one** — the app ships the same `index.html`, the same `game.js`,
the same 22 tracks that the live site serves. Everything iOS-specific lives in
this directory plus two feature-detected branches in `game.js` that no browser
ever takes.

## The one command

```
node tools/mkios.mjs
```

Assembles `ios/www` and regenerates the Xcode project. Run it before every
device build and before every archive — the payload is a **copy**, so a
`game.js` you just edited is not in the app until you re-run this.

Signing: `CS_TEAM_ID=XXXXXXXXXX node tools/mkios.mjs`. The project is generated,
so a team picked in Xcode's UI does not survive the next regeneration; the env
var is the durable answer.

The icon is generated too, from the game's own sprite sheet:

```
node tools/mkicon.mjs
```

It lifts `_CRAB_TOP` + `_CRAB_LEGS_W` and `PAL` straight out of `sprites.js`, so
the App Store art cannot drift from the crab that is actually in the game.
(It mirrors the left half onto the right: the walk cycle is drawn asymmetric,
which is correct for a crab that is moving and wrong for one standing still on
a home screen.)

## Build and run

```
open ios/CrabShack35.xcodeproj                     # or:
xcodebuild -project ios/CrabShack35.xcodeproj -scheme CrabShack35 \
  -destination 'platform=iOS Simulator,name=iPhone 17' build
```

Safari's Web Inspector attaches to the running app (Develop → the device →
CRAB SHACK); `web.isInspectable = true` is set unconditionally, which is the
right trade while the app is unreleased and one line to gate later.

## The four decisions worth knowing

**1. A custom `crabshack://` scheme, not `loadFileURL`.** A `file://` document
in WKWebView gets an *opaque* security origin, and localStorage on an opaque
origin is unreliable — it can read back empty on a later launch. The entire
save system is localStorage, so that is not a gamble worth taking.
`BundleSchemeHandler` serves the bundle over a real, stable origin, which makes
localStorage, WebAssembly and audio behave exactly as they do on the live site.

**2. The scheme handler answers Range requests.** WebKit's media loader asks for
byte ranges even though the game never seeks — every track arrives as
`Range: bytes=0-`. A handler that ignores Range and always answers 200 makes
playback flaky in a way that only shows up on a device.

**3. The web view is pinned to the safe area, not the screen.** `index.html`
centres the bezel in the viewport, so an edge-to-edge web view parks the home
indicator on top of the game's bottom rows. The band this leaves is painted
`#10182c` — the page's own background — so it reads as the page rather than as
a letterbox.

**4. Export goes through the share sheet.** Inside a web view an `<a download>`
is **inert**: the tap does nothing and reports nothing. `exportSlot()` detects
`window.webkit.messageHandlers.crabshack` and posts the save to
`SaveBridge.swift` instead. Import needs no bridge — `<input type="file">` opens
the document picker exactly as it does in Safari.

Save-on-background needs no bridge either: `game.js:21288` already saves on
`visibilitychange`, and WebKit fires that when the app backgrounds.

## What only a device can prove

The suite cannot see any of this. Walk it once per release:

- [ ] **localStorage survives a cold launch.** Play a day, force-quit from the
      app switcher, relaunch. The town is there. *This is the one that decides
      whether the custom-scheme call was right.*
- [ ] **Music plays**, and keeps playing across a track change (Range).
- [ ] **The mute switch silences it** and someone else's podcast survives launch
      (`.ambient` + `.mixWithOthers`).
- [ ] **Background/foreground loses nothing** — swipe away mid-day, come back.
- [ ] **Export** opens the share sheet and "Save to Files" writes a `.json`
      with the right name; **import** reads it back.
- [ ] **Rotate** portrait↔landscape. The page reloads by design (the 256×288 /
      256×240 mode flip); confirm the town survives the reload.
- [ ] **The home indicator never covers the game**, on a notched phone, in both
      orientations.
- [ ] **Ordering works** — select → SEND → place. This is the gesture that was
      impossible on phones before CS3.5.
- [ ] **Haptics** fire on a purchase and on a refusal, and *not* on every coin.
- [ ] **iPad**: the share sheet is a popover and does not crash (it is anchored,
      but anchoring is exactly the thing that silently rots).

## Shipping it

Everything below is Matt's to do, in App Store Connect:

1. **Bundle ID** — `com.groblegark.crabshack` is a placeholder in `project.yml`.
   Register the real one on developer.apple.com first; it must match.
2. **App record**: name, subtitle, category (Games → Simulation), age rating
   (the questionnaire; this game is clean but "infrequent/mild" is the honest
   answer on nothing at all).
3. **Screenshots** — 6.9" and 6.5" iPhone are required. They can come from the
   simulator. *Never screenshot the ending card* — the town's name is embargoed
   and the App Store listing is the most public surface there is.
4. **Privacy** — the app collects nothing, has no network calls, no analytics,
   no third-party SDKs. "Data Not Collected" is literally true; a privacy
   policy URL is still required.
5. **Export compliance** — already answered in `project.yml`
   (`ITSAppUsesNonExemptEncryption: false`), so the upload stops asking.
6. **Review risk, stated plainly**: guideline **4.2 (Minimum Functionality)** is
   the standing risk for anything web-view-shaped. The mitigations are in place
   — fully offline, no remote URL, no browser chrome, native share sheet,
   native haptics, native audio session — and a game with this much simulation
   in it is not what 4.2 was written for. If it is rejected anyway, the reply is
   a description of the sim, not a rewrite.
