# CS3.5 Runtime Options — Executing Cultureway Logic from a Save File (research dump, 2026-08-21)

**Framing constraint discovered during research:** the hardest requirement — "a mid-run continuation lives in a JSON save" — is only met off-the-shelf by ONE option (JS-Interpreter). Every other viable runtime forces (or invites) an architecture where cultureway logic is a **pure, re-entrant per-tick function** over plain-JSON state, so nothing mid-run ever needs saving. Ink is the proof this architecture ships in real games. Score serialization below with that in mind.

---

## 1. Sandboxed JS-in-JS interpreters

### Neil Fraser JS-Interpreter — https://github.com/NeilFraser/JS-Interpreter
- **Status:** active (pushed 2026-06-17), 2.2k stars, Apache-2.0. Docs: https://neil.fraser.name/software/JS-Interpreter/docs.html
- **What:** ES5-only AST interpreter, ~80 KB compressed bundle (acorn+interpreter), plain `<script>`, no build step. ~200x slower than native.
- **Metering:** `step()` executes one op — perfect fuel metering; bound a tick by counting steps. Multiple interpreter instances = cheap green threads (one per crab/institution).
- **Serialization:** THE headline feature. Paused execution — loops, closures, stack — serializes and resumes ("continuously executing programs that survive a server reboot"). Demo: https://neil.fraser.name/software/JS-Interpreter/demos/serialize.html. **Caveats (documented):** format is not human-readable, **not guaranteed stable across interpreter versions**, needs private API access (incompatible with the compressed bundle), and carries ~300 KB overhead because serialized polyfills ride along in every snapshot. So "continuation in save" works but bloats saves and version-locks them to an interpreter version — you'd vendor one interpreter version forever or migrate saves.
- **Sandbox:** no ambient authority by construction ("creates its own virtual machine with no external APIs" — whitelist, not blacklist). Known ReDoS hazard via regexp (docs ship Web Worker mitigations); simplest fix: disallow regexp in cultureway code.
- **Determinism:** numbers are host doubles → `+ - * /` are IEEE-exact everywhere, but `Math.sin`-class transcendentals vary by browser (same hazard CS3's own sim already lives with). Don't expose `Math.random`/`Date`; inject the game's seeded PRNG.
- **LLM-writability:** high, with one tax: models must be told **ES5 only** (no `let`, arrow fns, template literals) — a lint/transpile-free constraint LLMs violate casually; a validation pass (acorn parse with ES5 flag) catches it cheaply.

### sval — https://github.com/Siubaak/sval
- **Status:** alive-ish (pushed 2026-08-05; v0.6.12 npm 2026-04-12), 446 stars, MIT, 651 KB unpacked (acorn-based, TS). Supports partial ES2017+ syntax, `sandBox` option.
- **Metering/serialization:** none — runs code synchronously to completion; no step API, no state snapshot. An infinite `while(true)` hangs the tab.
- **Sandbox:** claimed, but no security process, tiny team; historically escapes via constructor chains have been the failure mode of this class of library (cf. vm2's 20+ CVEs and its Jan-2026 9.8-CVSS relapse: https://socradar.io/blog/cve-2026-22709-vm2-sandbox-escape-vulnerability/). For a local single-player game "sandbox" is about crash containment, not secrets — but the metering gap alone disqualifies it vs JS-Interpreter.
- **Verdict:** dominated by JS-Interpreter (metering+serialization) and quickjs (isolation+modern JS). Include in table, exclude from shortlist.

### quickjs-emscripten (+ quickjs-ng) — https://github.com/justjake/quickjs-emscripten
- **Status:** actively maintained (pushed 2026-07-23; npm 0.32.0, 2026-02-16), 1.7k stars, MIT. Engine choices: bellard/quickjs or **quickjs-ng** (https://github.com/quickjs-ng/quickjs — pushed 2026-08-21, 3.6k stars, MIT, 40+ contributors, ~2-month release cadence — the healthy fork).
- **Footprint:** release-sync variant ~500 KB wasm; asyncify ~1 MB; minimal install (core + one variant) ~1.3 MB. Loads as plain ESM from CDN (`import { getQuickJS } from "https://esm.sh/quickjs-emscripten@..."`) or jsdelivr IIFE — no build step, but it's the heaviest "small" option.
- **Metering:** `setInterruptHandler()` (fires every ~1024 ops — real fuel), `setMemoryLimit()`, `setMaxStackSize()`. Interrupt **aborts**, it doesn't pause — you can bound a tick but not suspend/resume mid-script (asyncify suspends only for host calls, and that state lives in the wasm stack, not JSON).
- **Determinism:** best in class — the entire engine incl. libm runs inside wasm, so float results are bit-identical across browsers. Must stub `Date`/`Math.random` inside the VM (trivial: evaluate a shim first).
- **Serialization:** none in quickjs-emscripten. Frontier: https://github.com/vercel-labs/quickjs-wasi snapshots a whole QuickJS-NG VM incl. pending promises — but as a multi-MB binary wasm-memory image, WASI/server-oriented; not a JSON-save citizen.
- **Sandbox:** strongest available — wasm linear memory boundary. Simon Willison's Mar-2026 sandboxing survey ranks it top for isolation: https://github.com/simonw/research/tree/main/javascript-sandboxing-research
- **LLM-writability:** the best of any option — modern JS, zero dialect tax.

## 2. Lua in the browser

### wasmoon (Lua 5.4 wasm) — https://github.com/ceifa/wasmoon
- **Status:** repo pushed 2026-07-29, 692 stars, MIT; but npm last published **2023-12-08** (1.16.0) — maintenance is real-but-thin, single-maintainer. 458 KB unpacked; ~393 KB plain / **130 KB gzipped** bundle; ESM; wasm embedded (hostable separately via factory).
- **Metering:** stock Lua 5.4 → `debug.sethook(fn, "", N)` count hooks = genuine instruction metering; hook can `error()` to abort a tick, and the run-each-cultureway-in-a-coroutine pattern allows preemptive yield (count/line hooks may yield in modern Lua — verify against 5.4 build before betting on it).
- **Determinism:** wasm float determinism like quickjs; must pin `math.randomseed`, stub `os.time/os.clock`. Even `pairs` order is reproducible given identical op history (no ASLR in linear memory).
- **Serialization:** none. **Eris/Pluto don't rescue it:** Eris (https://github.com/fnuecke/eris) persists yielded coroutines — the exact CS3.5 dream — but targets Lua **5.2/5.3** C builds and is dormant (Pluto, the original, is 5.1-era: http://mikehadlow.blogspot.com/2013/04/serializing-lua-coroutines-with-pluto.html). Getting Eris into the browser means maintaining a custom Lua-5.3+Eris emscripten build — a build step and a fork, both off-pillar.
- **LLM-writability:** excellent — Lua is the modding lingua franca; models write idiomatic Lua 5.x with very low error rates.

### fengari (Lua-in-JS) — https://github.com/fengari-lua/fengari
- **Status:** 2k stars, MIT, pushed 2026-01-02 but effectively maintenance-mode (fengari-web npm last published **2018**; open issues linger). Implements Lua **5.3** semantics; ~214 KB plain / 69 KB gz; plain `<script>` via fengari-web — the easiest no-build Lua.
- **Hazards:** **32-bit integers** (nonstandard Lua define — overflow behavior differs from every Lua 5.3 doc an LLM has read); math delegates to JS `Math` → cross-browser transcendental drift; ~25x slower than wasmoon on benchmarks (389 ms vs 15 ms heapsort, per wasmoon's README); no `__gc`/weak tables. `debug` mostly present, so count hooks work.
- **Verdict:** the "tiny + script-tag" Lua, paid for in speed, staleness, and integer weirdness.

## 3. Small embeddable languages
- **Wren** — https://github.com/wren-lang/wren: 8.1k stars, MIT, VM "<4,000 semicolons," but upstream is quiet (last push 2025-11) and the browser story is a dormant hobby port (https://github.com/ppvk/wrenjs — 33 stars, emscripten 2.0.21-era, 87 commits). Lovely language, no maintained browser artifact, thin LLM training data. Pass.
- **Gravity** (https://github.com/marcobambini/gravity, 4.5k, MIT, pushed 2026-08) and **Squirrel** (https://github.com/albertodemichelis/squirrel, 1k, MIT, pushed 2026-02): no maintained WASM/browser builds surfaced at all — you'd own the emscripten port. Pass.
- **BiwaScheme** — https://github.com/biwascheme/biwascheme: MIT, active (pushed 2026-08-20; 0.8.3 npm 2025-09), 1.55 MB unpacked, script-tag friendly, R7RS-small **with first-class continuations and TCO** — architecturally seductive (call/cc ≈ pausable agents) but continuations aren't JSON-serializable, and LLM Scheme output is markedly less reliable than JS/Lua. Niche.
- **Forth-likes** — WAForth (https://github.com/remko/waforth, 590 stars, MIT, pushed 2025-07): astonishing 10 KB wasm module, compiles to wasm on the fly. Determinism fine; metering awkward (it JIT-emits wasm — you meter at word granularity, not instruction); LLM-writability of Forth is the worst of any mainstream language. Curiosity, not a candidate. Tiny-lisp `fe` (https://github.com/rxi/fe, C, 1.5k stars) has no canonical JS/wasm port — it's more useful as a *blueprint for rolling your own* (~800 lines of C, allocation-free core) than as a runtime.

## 4. Declarative / expression layers
- **JsonLogic** — spec/original impl https://github.com/jwadhams/json-logic-js (1.5k stars, MIT, 65 KB npm, last push 2024 — coasting). The living implementation is **json-logic-engine** — https://github.com/json-logic/json-logic-engine (MIT, v5.0.7 npm 2026-04-01, 379 KB unpacked, faster, custom operators, and the json-logic org is writing a rigorous cross-impl spec). Rules ARE JSON → they live in the save file natively; guaranteed termination; zero ambient authority; state is only data. Weakness: LLMs writing deeply nested JsonLogic make bracket-soup errors at markedly higher rates than writing JS/Lua, and there's no comment syntax for self-documenting cultureways.
- **CEL** — the one-line-expression sweet spot ("`crab.molt_stage >= 2 && town.pot > cost`"). Landscape shifted in 2026: ChromeGG/cel-js is **archived** (2026-04, https://github.com/ChromeGG/cel-js); the successor is **@marcbachmann/cel-js** — https://github.com/marcbachmann/cel-js: MIT, zero-dep, v8.0.0 npm 2026-07-07, 227 KB unpacked, ESM+tree-shaking, macros/custom types, non-Turing-complete → always terminates. Expressions are strings → trivially save-file-resident. LLMs write CEL well (it's ~JS expression syntax).
- **jexl** — https://github.com/TomFrost/Jexl: genuinely sandboxed (no `Function`/`eval`), 88 KB, MIT, but **unmaintained since 2020** (npm 2.3.0, 2020-09). Usable, but CEL now dominates it on spec rigor and maintenance.
- **expr-eval** — **DISQUALIFIED**: CVE-2026-12866, CVSS 9.8, arbitrary code execution via `toJSFunction()`/`new Function`, all versions, no full fix possible by design (https://threat-modeling.com/cve-2026-12866-expr-eval-javascript-code-execution/).

## 5. Rolling your own
- Canonical text: **Crafting Interpreters** (Nystrom) — free online, walks a complete tree-walker (jlox) and a bytecode stack VM (clox): https://craftinginterpreters.com/chunks-of-bytecode.html + https://craftinginterpreters.com/a-virtual-machine.html. clox is on the order of 2.5k lines; Wren, the same author's production-grade version, stays "<4,000 semicolons." A JS port sized for CS3 (no classes, no GC cleverness — lean on the host) plausibly lands at 1.5–3k lines, i.e., ~15–20% of game.js.
- **The killer argument for it:** if the VM's whole machine state is *designed* as plain arrays (stack, pc, globals, frames), then mid-run continuations serialize to JSON **for free, forever, with a stable format you own** — the thing no off-the-shelf option delivers cleanly. Fuel metering is a `--fuel` decrement in the dispatch loop. Determinism is total because you define the numerics.
- **Shipped precedents:** **Ink** (inkle) is exactly this pattern in production — a purpose-built narrative language compiled to a JSON runtime format (https://github.com/inkle/ink/blob/master/Documentation/ink_JSON_runtime_format.md) with JSON-serializable resumable story state; the JS runtime inkjs is MIT, active (v2.4.0, 2026-02, https://github.com/y-lohse/inkjs). **Stationeers' IC10** — in-game MIPS-like VM, 128-line programs, machine state persists in saves. **Else Heart.Break()'s Sprak** — whole-world programmability on a bespoke interpreted language (https://en.wikipedia.org/wiki/Else_Heart.Break()). **Screeps** meters player JS by CPU via isolated-vm (server-side; per https://github.com/simonw/research/tree/main/javascript-sandboxing-research).
- **The killer argument against:** LLM-writability. CS4's premise is agents authoring cultureways; a bespoke language means every authoring agent burns context on a language spec and hallucinates syntax at a rate JS/Lua never would. Mitigation: make the bespoke VM's *surface syntax a strict JS or Lua subset* (parse with acorn/an off-the-shelf Lua parser, compile to your own serializable bytecode) — models write a language they already know; you own only the back half.

## THE REALISTIC SHORTLIST

1. **JS-Interpreter** — *the "scripts are alive inside the save" bet.* Only option where a crab's half-finished ritual (`walkTo(townHall); castBallot(); ...`) pauses mid-line and rides the JSON save. Cost: ES5 dialect tax on LLM authors, ~200x interpreter speed (fine for cultureway-level logic, not per-frame), snapshot bloat + a format you must version-pin. Apache-2.0, healthy.
2. **quickjs-emscripten + quickjs-ng** — *the "real JS, real sandbox, bit-perfect determinism" bet.* LLMs author in the language they're best at; strongest isolation and cross-browser float determinism of anything surveyed. Cost: ~1 MB of wasm in a hand-crafted vanilla-JS game, and NO mid-run serialization — forces the Ink-style architecture (cultureway = pure `step(stateJSON, event) → stateJSON'`), which is arguably the better design anyway.
3. **wasmoon (Lua 5.4)** — *the "games script in Lua" bet.* Best metering primitive (`debug.sethook` count hooks), deterministic wasm core, the language modders and models both know cold. Cost: single-maintainer with a stale npm, and the Eris coroutine-persistence dream is a version-mismatched dead end — same re-entrant-tick architecture required as #2.
4. **Data + CEL/JsonLogic hybrid** (`@marcbachmann/cel-js` or `json-logic-engine`) — *the "cultureway is a document, not a program" bet.* Perfect fit with every CS3 pillar: guaranteed termination, zero ambient authority, conservation checkable statically, save-file-native, tiny. Cost: not Turing-complete — cultureways become configurations of engine-provided verbs (elections, pots, counts) plus formulas, so radically alien cultureways (new *mechanisms*, not new *parameters*) stay out of reach — which is exactly the CS4 question this research feeds.

**Cross-cutting finding for the synthesizer:** options 2–4 all converge on the same architecture (program-as-data + pure tick function + state in plain JSON, as proven by Ink); option 1 is the lone off-the-shelf path to true resumable-script saves; roll-your-own (Crafting Interpreters + a JS-or-Lua-subset front end feeding a JSON-serializable bytecode VM) is the only path that gets *both* resumable saves *and* a stable owned format — at the price of becoming a language maintainer.
