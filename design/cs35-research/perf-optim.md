## Hot spot 1 — `collide` (game.js:6957–7027, ~16.2% self)

**1a. AABB early-out before `Math.hypot` in the pairwise loop — GREEN.** At 6966–6967, `d = Math.hypot(dx, dy*1.8)` is computed for every pair before any test; both consumers (`d < 12` at 6968, `d < 12 + BERTH_PX` at 6986, BERTH_PX=10 so both constants ≤22) are provably false when `|dx| >= 22 || 1.8*|dy| >= 22`, since `hypot(a,b) >= max(|a|,|b|)`. Insert `if (dx > 22 || dx < -22 || dy > 22 || dy < -22) continue;` after line 6966 (dy is already pre-scaled). No state is touched for skipped pairs under current code; pairs that survive compute the *identical* hypot with identical float ops in identical order; RNG untouched. With ~10–14 bodies spread over a ~1200px world, most of the 50–90 pairs are far apart most of the frame — expect 60–85% of hypot calls skipped. **Gain ~5–8% of total CPU.** Risk: none if written as a pure skip. Verify: STD-VERIFY incl. position hash. Do NOT replace `Math.hypot` with `sqrt(dx*dx+dy*dy)` — hypot is a different (correctly-rounded-ish, overflow-safe) algorithm and results differ in the last ulp, which the fingerprint discipline forbids: **RED** ([WebKit bug 284631](https://bugs.webkit.org/show_bug.cgi?id=284631), [V8 Math.hypot internals](https://blog.seokho.dev/development/2024/03/18/V8-optimize-MathHypot.html), [numpy #14761](https://github.com/numpy/numpy/issues/14761)).

**1b. Hoist per-frame furniture/station structures — GREEN.** Line 6991 rebuilds `(bizTables(bizKey)||[]).concat(BIZ[bizKey].stalls||[])` per biz per frame (and `bizTables` at 4870 `.slice()`s for shack), and lines 6989/7006 call `Object.keys(BIZ)` twice per frame (42 `Object.keys(BIZ)` sites file-wide). Cache: module-level `BIZ_KEYS` const; per-biz furniture array memoized on `(TABLE_BASE + UPS.table.lvl, unlock state)` — table level and stalls change only on purchase, so invalidate via a generation counter bumped at the handful of purchase sites. Same array contents, same iteration order, zero float/RNG impact. **Gain ~1.5–2.5%** (the concat/slice churn plus keys allocation). Verify: STD-VERIFY.

**1c. Spatial sweep/grid broad phase — YELLOW, not recommended.** A sort-by-x sweep changes *pair visit order*, and pushes at 6973–6984 mutate x/y that feed later pairs in the same pass — pair order is behavioral here. It could be built to emit pairs in the exact original (i,j) order, but with n≈14 the win over 1a is negligible. Skip.

## Hot spot 2 — scheduling-derivation chain (~25% aggregate: refreshDaysOff 4008, dayOffIdx 4038, coveringToday 4047, bizShiftWindow 4091, dutyShift 4105, effShift 4197, updateSchedule 7321, leaveGmin 6885)

**2a. Kill the per-call sig rebuild in `refreshDaysOff` via a roster generation counter — YELLOW (auditable to GREEN).** Line 4017 builds `sig = allCrabs().map(k => k.p.name + "|" + k.p.job).join(",")` on *every call before* the memo check at 4018 — ~50+ builds/frame × 7200 frames/day. Replace the string compare with `if (_offStamp === time && _offGen === rosterGen) return;` where `rosterGen` is a module counter bumped at every site that changes roster membership or `p.job`/`p.name`. The audit is bounded and I've enumerated it: **14 crabs/npcs array-mutation sites** (3285, 3289, 5109, 6426, 6491, 6503, 7205, 7249, 7289, 8197–8198, 16124) and **15 `p.job` assignment sites** (2271, 2275, 2359, 2814, 3143, 4535, 6483, 7184, 7323–7324, 8231, 10608, 10882, 15585). Note 7323–7324 sit *inside* `updateSchedule` — the counter must be bumped there so a mid-frame job reassignment invalidates for the next crab in the same frame, exactly reproducing the current sig-compare semantics (this is precisely the BRASS-buys-the-Driftwood bug the comment at 4009–4016 documents; a stamp-only memo would reintroduce it). With the bump in place this is semantically identical, hence GREEN-after-audit; classified YELLOW only because a missed mutation site fails silently — which is exactly what the suite's frozen fingerprints will catch. Also have the rebuild write `c._offIdx` onto each crab (predeclare the field at crab creation for hidden-class stability) so `dayOffIdx` (4040) becomes a field read instead of a `name+"|"+job` string build per lookup. **Gain ~8–12% of total CPU** — the largest single win available (refreshDaysOff 6.1 self + most of dayOffIdx 2.9 + part of coveringToday 3.3 is sig/key string work). Verify: STD-VERIFY plus targeted scenarios: business handover, hire, death, `--nohall`.

**2b. Memoize `bizShiftWindow` per (biz, kind) on (h.open, h.close), and make `label` lazy — GREEN with one audit.** Lines 4091–4100 allocate `{start,end}` (via `capWindow`) and format `w.label = fmtHr()+"-"+fmtHr()` on every call; grep confirms shift-window `.label` is read **only in draw/UI code** (12219, 13251–13252, 13544 — dossier and signage), never in sim logic, and headless never renders. Cache per biz+kind, invalidate by comparing two numbers (open/close); compute label once at cache fill (keeps the object shape identical and the UI unchanged — cheaper than a getter and zero behavioral surface). One audit: confirm no caller mutates the returned window object (callers read `.start/.end`; `effShift`'s OT path at 4200 builds its own fresh object — safe; grep for `\.(start|end) =` on shift vars to close it). **Gain ~2–3%** (bizShiftWindow 2.2 self + allocation/format share inside dutyShift/effShift cum). Verify: STD-VERIFY.

**2c. Per-crab per-frame shift memo — YELLOW, second wave only.** `updateSchedule` re-derives the chain repeatedly per crab per frame (effShift at 7322, leaveGmin→effShift again at 7340, dutyShift+otEligible again at 7349–7350). A `c._shift = {stamp, gen, eff, duty}` memo keyed on (frame counter, rosterGen) would cut 3–4 rederivations to 1. **Trap, measured in the code**: `sh` computed at 7322 is used at 7340 *after* lines 7323–7324 may reassign `c.p.job`, while `leaveGmin(c)` at 7340 recomputes with the NEW job — the current code is inconsistent-by-accident and that inconsistency is frozen; a naive memo filled at 7322 would change the job-reassignment frame. The memo must be invalidated by the rosterGen bump from 2a (which 7323–7324 triggers), making it correct by the same mechanism. **Gain ~2–4%** on top of 2a/2b. Do it only after 2a lands and is proven. Verify: STD-VERIFY, plus a dedicated seed where a shop changes hands.

## Hot spot 3 — `allCrabs` (5068, 3.0% self, 83 call sites)

**3a. Generation-counter cached concat — GREEN.** `return npcs.length ? crabs.concat(npcs) : crabs` — fresh ~12-element array per call, many calls per frame. Cache the concat result; invalidate by bumping the same counter at the 14 array-mutation sites from 2a (identical audit list — one counter serves both). Two semantics to preserve exactly: (i) when `npcs.length === 0` the function returns the **live** `crabs` array, not a snapshot — keep that branch untouched; (ii) invalidation must build a **new** array (never mutate the cached one) so an in-flight `for...of` over a stale snapshot behaves exactly like today's fresh-concat snapshot. Callers only read/filter/map (verified in refreshDaysOff, cotRoster, frame loop; a final `allCrabs()\.(sort|push|splice)` grep should come back empty before landing). **Gain ~2.5–3%.** Verify: STD-VERIFY.

## Hot spot 4 — vm-global hatch flags (`patOff` 5279 = 1.8%, plus `window._no*` reads in needDrag 5793–5794, heatShimmer 5807, `window._stats`, `window._nocollide` 15891, ~20 sites)

**4a. Hoist flags to module locals refreshed once per frame — GREEN in practice.** In the Node vm the contextified global is slow to read; `patOff` alone (`!!(window._failOff && window._failOff[k])`) burns 1.8% across its 5 gates (5461, 7053, 8600, 8712, 15743). At the top of `frame()`, copy `_failOff`, `_noNeedDrag`, `_noSelfCareExempt`, `_noShimmer`, `_stats`, `_nocollide` into module-scope vars; hot functions read those. The harness sets these flags once at boot (suite arm-off hatches) — a ≤1-frame propagation delay is unobservable in every existing use; in the browser this is a no-op cost-wise but harmless. This is a real-engine optimization, not a headless fast path — the same code runs in the browser. **Gain ~2.5–3.5%.** Verify: STD-VERIFY with every hatch exercised: `--failoff`, `--nohall`, `--norival`, etc. — the suite already runs these.

**4b. Hoist `needDrag`'s `ramp` closure (5795) to module scope — GREEN.** It's a pure arrow allocated per call and profiles at 1.0% on its own; lift it to a module function (or inline the two applications). Same float ops, same order. **Gain ~0.8–1%.** Verify: STD-VERIFY (needs-bite and anti-spiral scenarios cover this arithmetic).

## Hot spot 5 — customers/visitors (updateCustomers 9932 = 3.3%, visTick 9755 = 2.3%, visStep 1.2%, queueOrder 9906)

**5a. Hoist the needs-key array in `visTick` — GREEN, trivial.** Line 9779 evaluates `["hunger","thirst","dirt","bored","tired"]` per visitor per frame; lift to `const VIS_NEEDS = [...]` at module scope. Iteration order unchanged. **Gain ~0.5–1%.** Verify: STD-VERIFY.

**5b. Single-pass queue bucketing — GREEN.** Lines 9939–9940: per frame, `queueOrder(b)` runs `customers.filter(...)` + `.sort()` per biz (9907–9909), i.e. B full scans of the customers array plus B fresh arrays plus a fresh `Map`. Replace with one pass over `customers` bucketing `inLine` members per biz into reused (cleared, not reallocated) arrays, then the same `(a,b) => a.qSeq - b.qSeq` sort per bucket. `qSeq` is unique and monotonically assigned (9929), so sort output is fully determined by the key set — bucket fill order (which preserves customers-array relative order, same as filter) cannot change the result; `queueJoin` at 9908 still fires in the same encounter order. Keep the standalone `queueOrder` for its other callers or reimplement it over the buckets. The `qslot` Map can be reused (clear per frame). **Gain ~1–1.5%.** Verify: STD-VERIFY plus the close-queue tracking scenario (`trackCloseQueues` reads line state).

**7a. Frame bookkeeping micro-hoists — GREEN, small.** The timer chain 15389–15396 and rollover branch are irreducible dispatch; the real extractables are the `allCrabs()` loop headers at 15403/15848/15872 (covered by 3a) and `Object.keys(BIZ)` hoists (covered by 1b). **7b. Engine behavior untouched by definition; it's harness throughput only, allowed because it forks no game logic. **Gain ~3–4% of wall CPU in headless runs.** Verify: matrix diff only (suite fingerprints unaffected by tools timing).

## V8-specific findings relevant to this code shape

- **Allocation rate, not GC pauses, is the bill here** — the profile shows it: explicit GC is only 0.8–1.1% because everything is scavenger-friendly young-gen garbage, but the *allocators* (concat, closures, string builds) pay inline. The 2025/26 consensus: reducing allocation rate in hot loops still wins; classic **object pooling is only worth it for high-volume same-shape objects** (particles), and for this game's shapes (a dozen crabs) elimination-by-caching beats pooling — pooled objects that get referenced from old-gen state add write-barrier cost. All candidates above are elimination, not pooling. ([V8 Orinoco scavenger](https://v8.dev/blog/orinoco-parallel-scavenger), [Trash talk](https://v8.dev/blog/trash-talk), [v8-perf GC notes](https://github.com/thlorenz/v8-perf/blob/master/gc.md), [GC pauses & allocation rate](https://dev.to/helloashish99/javascript-gc-pauses-allocation-rate-frontend-jank-3jig))
- **Hidden-class stability**: crabs and npcs are built by different constructors (`newCrab`, npc spawn at 5109/3285); if their shapes differ, every hot function taking `c` (updateSchedule, collide, crabMove) runs polymorphic ICs, and >4 shapes goes megamorphic. Any new cached field (`c._offIdx`, `c._shift`) must be initialized at creation in *both* paths, in the same property order — never added lazily on first memo fill. Worth a one-off `%HaveSameMap`-style check (or just consistent init discipline). ([hidden classes & ICs](https://medium.com/@yashschandra/hidden-v8-optimizations-hidden-classes-and-inline-caching-736a09c2e9eb), [shapes & deopt guide](https://kislayvats.com/blogs/v8-hidden-classes-optimizing-object-shapes), [V8 deopt tiers](https://www.thenodebook.com/node-arch/v8-engine-intro))
- **String concat in hot paths**: V8 ropes make single concats cheap, but the sig at 4017 forces flattening via `.join` and creates ~13 intermediate strings per call, 50+ calls/frame — elimination (2a) beats any concat micro-tuning.
- **`Math.hypot` is known-slow in V8** (Torque builtin with precision/overflow handling; several×  slower than `sqrt(x*x+y*y)`), but swapping it changes ulps — **RED, forbidden**; the AABB skip (1a) captures most of the win without touching a single computed float. ([WebKit 284631](https://bugs.webkit.org/show_bug.cgi?id=284631), [Seokho V8 hypot analysis](https://blog.seokho.dev/development/2024/03/18/V8-optimize-MathHypot.html))
- **Typed arrays for x/y/needs**: Float64Array preserves double semantics exactly, but restructuring crab state is a mass refactor across 16k lines with save-format and iteration-order exposure for single-digit upside — not worth it at this scale (14 bodies). RED-by-blast-radius; do not pursue.
