# PRECEDENTS: CODE LIVING IN THE SAVE/WORLD FILE — research dump

Scope: LambdaMOO/MUD softcode, Minecraft datapacks, Factorio, Dwarf Fortress, Screeps, Smalltalk images / HyperCard stacks, plus adjacent precedents (Second Life LSL, Zachtronics saves). Per system: code representation in the file, trust/sandbox model, resource limits, versioning/migration, failure modes. Payoff section at end.

---

## 1. LambdaMOO / MUD softcode — "the program IS the database"

**Representation.** The MOO is a single in-memory object database, periodically checkpointed to a portable **plain-text .db dump**; that dump contains every object, its properties, AND the source text of every verb — "the database contains representations of all the objects in the virtual reality, including the MOO programs that the server executes to give those objects their specific behaviors" ([MOO-Cows FAQ](https://www.moo.mud.org/moo-faq/moo-faq-2.html); [LambdaMOO source archaeology](https://gioorgi.com/2018/exploring-23-years-old-lambdamoo-2/): "LambdaMoo is composed of an object database, dumped to a text file"; server source: [github.com/wrog/lambdamoo](https://github.com/wrog/lambdamoo)). A **verb** is a named MOO program attached to an object — method + user command in one; the parser dispatches typed commands to verbs via arg specifiers (`this none this`, prepositions) ([Programmer's Manual, Verbs](https://tecfa.unige.ch/guides/MOO/ProgMan/ProgrammersManual_7.html)). Suspended tasks (running computations!) checkpoint into the DB too — even in-flight code survives a restart ([MOO-Cows FAQ](https://www.moo.mud.org/moo-faq/moo-faq-2.html)). Server behavior is bootstrapped from the DB: on restart it calls `#0:server_started`; core services are properties on system object `#0` (`$room`, `$player`, `$server_options`).

**Trust model (the canonical design).** Per-verb permission bits **r/w/x/d**: `r` = non-owners may read source, `w` = non-owners may edit, `x` = callable from other programs, `d` = errors raise (catchable) vs. silently return error values ([Verbs chapter](https://tecfa.unige.ch/guides/MOO/ProgMan/ProgrammersManual_7.html)). Crucially, **verbs run with the permissions of their OWNER, not the caller** — setuid semantics: "the program in a verb can do whatever operations the owner of that verb is allowed to do and no others." Wizards are root ("the ability to change anything within the database"); only wizards reassign verb ownership; a **programmer bit** gates who may write code at all; **object quota** rations creation per player ([LambdaCore getting started](https://www.moo.mud.org/moo-faq/lcore-getting-started.html)). So the trust model is: everyone can run everyone's code, identity-based privilege, capability-ish via setuid verbs + property permissions.

**Resource limits.** Every task gets a budget of **ticks** (VM instructions, order tens of thousands — "last I looked I think it was 40,000 ticks") and wall-clock **seconds**; exceeding either aborts the task with an error; long jobs must voluntarily `suspend()` to refresh the budget (`$command_utils:suspend_if_needed`) ([darksleep MOO tutorial](https://www.darksleep.com/notablog/articles/LambdaMOO_Programming_Tutorial)). Budgets are DB-tunable via `$server_options` (fg/bg ticks and seconds) ([Programmer's Manual](https://tecfa.unige.ch/guides/MOO/ProgMan/ProgrammersManual_7.html), [lisdude archwizard FAQ](https://lisdude.com/moo/archwizard_faq.html)). Single-threaded cooperative scheduler.

**Versioning/migration.** Essentially none at the language level — the DB text format is versioned but the *core* (LambdaCore) is upgraded by porting verbs by hand; objects have permanent never-reused object numbers, and heavily-referenced objects become undeletable in practice (the FAQ notes an object "so large that he can't be deleted in the conventional manner"). Forking a community = copying the DB.

**Where it got messy.**
- **Scale**: the 1994 Wired-article population surge produced chronic **lag** — single-threaded scheduler, in-memory DB bloat from unchecked user object proliferation on 1990s hardware, crashes ([Encyclopedia of New Media](https://sk.sagepub.com/ency/edvol/newmedia/chpt/lambdamoo), [LambdaMOO Wikipedia](https://en.wikipedia.org/wiki/LambdaMOO)).
- **Governance became the content**: wizards tried to abdicate social power ("LambdaMOO Takes a New Direction," Dec 1992 — [LTAND text](https://sites.cc.gatech.edu/classes/AY2001/cs6470_fall/LTAND.html)); a **petition/ballot system implemented in softcode** followed (30-day residency to vote, wizardly vetting, signature thresholds, 66% to pass — [Mnookin, "Virtual(ly) Law"](https://onlinelibrary.wiley.com/doi/full/10.1111/j.1083-6101.1996.tb00185.x)); triggered by the "Mr. Bungle" abuse case ([A Rape in Cyberspace](https://www.villagevoice.com/a-rape-in-cyberspace/)); wizards later partially took power back ("LTAND II") ([MUD wiki](https://mud.fandom.com/wiki/LambdaMOO)). **Directly relevant to CS3**: a game whose government is data ends up governing the data.
- **Softcode vs hardcode split across the MUD family**: softcode (MUSHcode, MOO-code) is stored in the sim and interpreted at runtime, giving live in-world creation and a "simulation-like" feel; LPC hardcode is the server itself. "Most custom coding, for the sake of simplicity, security, and stability, is done in softcode rather than by directly modifying the hardcode" ([Softcode, MUD wiki](https://mud.fandom.com/wiki/Softcode); [LPC](https://mud.fandom.com/wiki/LPC); [LPMud](https://en.wikipedia.org/wiki/LPMud)). LPC's pass-by-reference of mappings was a real security hole class: pass a mapping holding access-control data and the callee can mutate it to escalate ([LPC, MUD wiki](https://mud.fandom.com/wiki/LPC)). MUSHcode's own lesson: a functional/macro string language that non-programmers could grow into, but famously write-only ([PennMUSH "Enough to be dangerous"](https://community.pennmush.org/book/export/html/21)).

## 2. Minecraft datapacks — declarative data + a command language, shipped inside the world

**Representation.** A datapack is a folder or zip **inside the world save** (`saves/<world>/datapacks/`), containing namespaced **JSON** (advancements, loot tables, recipes, predicates, dimensions, worldgen, tags) and **`.mcfunction`** text files — one command per line, no leading slash ([Data pack, minecraft.wiki](https://minecraft.wiki/w/Data_pack); [Creating a data pack tutorial](https://minecraft.wiki/w/Tutorial:Creating_a_data_pack)). Data-driven overrides need no engine code: "override or add new advancements, dimensions, functions, loot tables, predicates… without any code modification." Behavior hooks: `#minecraft:load` (world load/reload) and `#minecraft:tick` (every tick) function tags ([Function, minecraft.wiki](https://minecraft.wiki/w/Function_(Java_Edition))).

**The accidental language.** mcfunction has no real variables: state lives in **scoreboards** (32-bit ints attached to entities/fake players), **NBT data storage** (structured data, read/written via `/data`, bridged to scores via `execute store`), and since 1.20.2 **macros** (string-substitution into commands — slow) ([MCFunction vs Coding, datapack.wiki](https://datapack.wiki/guide/mcf-vs-code)). Control flow: conditionals are `execute if/unless` prefixes; loops are recursion or once-per-tick functions; no inheritance, no user types, no sqrt/trig/abs — community libraries hand-roll math. Called functions execute **within the caller's tick** (everything is synchronous within a tick), bounded by gamerule `maxCommandChainLength` (default **65,536** commands; excess silently ignored) ([Function](https://minecraft.wiki/w/Function_(Java_Edition))). This is a de-facto language that *evolved out of* command blocks + NBT rather than being designed — enormously productive, notoriously baroque.

**Trust model.** Functions run at **permission level 2** (server-configurable via `function-permission-level`) — i.e., datapack code runs as a semi-privileged operator, not as an untrusted guest; sandboxing is by construction (commands can only do what commands do — no I/O, no network). Trust is social: you install a pack into your world.

**Versioning/migration.** `pack.mcmeta` declares `pack_format`; the format number bumps **constantly** (split into separate data/resource formats in 1.17-era 20w45a; replaced by `min_format`/`max_format` ranges in 25w31a because per-version pinning was unmaintainable) ([Pack format](https://minecraft.wiki/w/Pack_format)). The 1.13 "Flattening" renamed all block/item IDs and broke everything ([1.13 resource pack changes](https://minecraft.wiki/w/Java_Edition_1.13/Resource_pack_changes)). The engine migrates its *own* NBT data across versions (DataFixerUpper) but does **not** migrate datapack code — packs just break and warn, and the ecosystem carries the maintenance burden ([community complaint](https://feedback.minecraft.net/hc/en-us/community/posts/41129865810957-Make-pack-format-consistent-with-data-version)).

**Failure modes.** Silent truncation at command-chain limit; version churn; the language's poverty pushes serious authors to external compilers that emit mcfunction — i.e., the in-save language became a compilation *target*, not an authoring surface.

## 3. Factorio — code OUTSIDE the save, state INSIDE, determinism as law

**Representation.** Mods are external Lua packages; the save embeds the **mod list + versions + startup settings + each mod's `storage` (née `global`) table** — serialized data only. "No variables or functions defined in [startup stages] will carry over" — the engine persists exactly one Lua table per mod, and it must be plain data: functions/closures don't serialize; metatables persist only if registered via `LuaBootstrap::register_metatable` ([Data lifecycle, lua-api.factorio.com](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html)). Three-stage lifecycle: settings → prototype ("data") stage builds the static world definition → control stage runs the sim. On load, mod `control.lua` re-executes to re-register event handlers, then `on_load` may ONLY restore metatables, conditional handlers, and local references — "doing anything other than [those] will lead to desyncs."

**Trust model.** Mods are fully trusted Lua within the game API (no OS access via the modding API surface), but the binding discipline is **determinism, not sandboxing**: multiplayer is deterministic lockstep, so any mod state outside `storage`, any RNG outside the game's, any iteration-order dependence ⇒ **desync**, the signature failure mode. Save/load itself must be a fixed point: "for a given save file: saving, exiting, and loading the save shouldn't change any observable behavior," because joining a multiplayer game IS save+load, and replays require it ([Rseding91, Deterministic save/load in Factorio](https://gist.github.com/Rseding91/a309cf0a30782a2e96ef081c39326f42) — includes details like saving entities in reverse order so load reconstructs ordering, and why load is far harder: pointer restoration, type migrations, error recovery).

**Versioning/migration — the gold standard.** Mods ship `migrations/*.lua` and `*.json`: JSON migrations rename prototypes (entity/item/tech IDs) in the save; Lua migrations rewrite `storage`/world state; applied once, ordered by mod order then filename lexicographically ([Migrations, API docs](https://lua-api.factorio.com/1.1.70/Migrations.html)). `on_configuration_changed` fires whenever game version, mod versions, mod set, startup settings, or prototypes changed, with full permission to fix up state ([Data lifecycle](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html)). The engine additionally maintains an ID mapping in the save ("what everything was saved as, what changed, what was removed") loaded before anything that uses IDs.

**Lesson.** Factorio is the strongest *counter*-example: it deliberately keeps code OUT of the save and re-binds saved data to versioned external code, spending its complexity budget on migrations + determinism instead of sandboxing. The cost: a save without its mods is crippled (content vanishes); mod-set identity is part of save identity.

## 4. Dwarf Fortress — raws (data-as-behavior) frozen into the save

**Representation.** The "raws" are plain-text token files (`[CREATURE:…]`, reactions, materials, entities) that define most of the game's content — data so expressive it borders on behavior. **On worldgen the raws are copied into the save** (`data/save/REGION/raw/`), so each world carries the exact definitions it was generated with; the engine's binary state (`world.sav`/`world.dat`) sits beside them ([Saved game folder](https://dwarffortresswiki.org/index.php/DF2014:Saved_game_folder); [Raw file](https://dwarffortresswiki.org/index.php/DF2014:Raw_file)).

**Trust/limits.** None needed — raws are declarative; no computation, hence no sandbox, no budgets. (The community bolted computation on *outside* the save via DFHack.)

**Versioning/migration.** Editing raws inside a live save works "to an extent": some token changes are safe, others corrupt; "duplicating the raw files can cause strange, difficult-to-diagnose problems, and even crashes"; "it is currently unknown how much these can then be changed without breaking the save" ([Raw file](https://dwarffortresswiki.org/index.php/DF2014:Raw_file)). Steam-era v50 formalized it: mods are **"baked in" at worldgen** and can only be *updated* to versions the game deems compatible via `[NUMERIC_VERSION]` checks, with patching functions instead of editing vanilla raws in place ([Modding](https://dwarffortresswiki.org/Modding)).

**Lesson.** Copy-on-worldgen gives perfect reproducibility per world and protects old worlds from new content — but creates an undocumented compatibility surface ("which edits break a live save?") the moment players touch the frozen copy, because engine binary state holds *derived* references into the raws.

## 5. Screeps — the player's program is the player, running 24/7

**Representation.** Player JS lives server-side (branches/modules, committed via API); it is not in a "save file" but it IS the persistent world-behavior artifact — the world runs it every tick whether you're online or not. Persistent *state* is strictly separated: the `Memory` object, auto-serialized via `JSON.stringify`/parsed on first access each tick, capped at **2 MB** per player, with `RawMemory` for custom serialization; parse cost bills to your CPU; game objects must be stored as IDs, never live references ([Global Objects docs](https://docs.screeps.com/global-objects.html)). Code cache regenerates on commit; nothing outside `Memory` reliably persists ([architecture](https://docs.screeps.com/architecture.html), [forum: How does Memory work?](https://screeps.com/forum/topic/3026/how-does-memory-work)).

**Sandboxing.** Originally Node's `vm` module — scripts "were not fully isolated from each other and the parent environment, sharing heap memory, garbage collection, and event loop." Marcel Laverdet wrote **isolated-vm** to wrap each player in a genuine V8 isolate: own heap, own GC, transferable between threads ([Screeps optimizations roadmap](https://blog.screeps.com/2017/06/optimizations/); [PTR changelog: isolated VM](https://screeps.com/forum/topic/2073/ptr-changelog-2018-01-18-isolated-vm); [changelog 2018-03-05](https://blog.screeps.com/2018/03/changelog-2018-03-05/)). Heap capped (~256 MB effective; exceed it and "your VM may be reset"). The history is itself the lesson: they shipped the naive sandbox first and were forced to a hard-isolation model.

**Resource limits.** Per-tick CPU limit (20 free / GCL-scaled with CPU Unlock); unused CPU accumulates in a **bucket** up to 10,000, drawable at up to 500 CPU in one tick for bursts; scripts exceeding the limit are **terminated mid-execution** "even if it has not accomplished some work yet" ([CPU limit docs](https://docs.screeps.com/cpu-limit.html)). Consequence: player code is written defensively around preemption — idempotent per-tick planning, state machines in Memory, no long transactions. Shard3 runs everyone at 20 CPU as a hard-limited economy.

**Lesson set.** (a) Hard budget + kill-at-limit + savings bucket is a complete, legible resource economy; (b) strict code/state separation with a size-capped JSON state blob keeps the world recoverable no matter what the code does; (c) real isolation (separate heaps) was non-negotiable once code was adversarial or merely buggy at scale.

## 6. Smalltalk images / HyperCard stacks — the document that contains its own code

**Smalltalk.** The image is "a serialized snapshot of a program's complete runtime state — heap, threads, stacks" — code and data fused, resumable for decades. Gilad Bracha's critique ([An Image Problem](https://gbracha.blogspot.com/2009/10/image-problem.html)): (1) **accumulated corruption** — failed runs leave mess you must clean rather than restarting fresh; (2) images **conflate code with computation state**, aggravating versioning and code extraction; (3) no stateless representation — "what is important is that you do not have *just* an image." Community consensus echoes it: "you should be committing source code, not saving your image… rebuild the image frequently from source"; the versioning/collaboration gap is blamed for Smalltalk's limited commercial success ([HN thread](https://news.ycombinator.com/item?id=36163383), [On Learning Smalltalk討论](https://news.ycombinator.com/item?id=29890205), [image-based development overview](https://peerdh.com/blogs/programming-insights/smalltalk-image-based-development)). Modern Smalltalks survived only by adding out-of-image source (Monticello/Git, Tonel) and treating the image as a build product.

**HyperCard.** Every object (stack, background, card, button, field) carries a **HyperTalk script** inside the stack file; message-passing hierarchy; users "begin by creating content and gradually add behavior" — the definitive gentle-slope end-user programming UX ([Dr. Dobb's 1988 intro](https://jacobfilipp.com/DrDobbs/articles/DDJ/1988/8814/8814d/8814d.htm); [HyperCard's Legacy](https://medium.com/@avonliden/hypercards-legacy-the-revolution-we-lost-2819ca0b63ac)). Failure modes: because documents carry live code and stacks copy scripts between each other, HyperCard got **viruses** — *merryxmas* (written in HyperTalk) copies itself from an opened infected stack into the Home stack, then into every stack subsequently opened; a typo in the virus caused it to splice random fragments of host scripts along with itself, corrupting behavior; hostile variants (CrudShot) deleted stacks; antivirus signature evasion via one-word edits ([HyperActive Software virus page](https://www.hyperactivesw.com/hypercard/virus1.html); [List of HyperCard viruses](https://en.wikipedia.org/wiki/List_of_HyperCard_viruses); [Apple KB via 512 Pixels](https://512pixels.net/2017/12/kbase-week-hypercard-merryxmas/)). Versioning lesson: stacks forked freely with no diff/merge — every shared stack was a new lineage; the ecosystem was unmaintainable at scale and died with the platform.

## 7. Adjacent precedents (brief)

- **Second Life / LSL**: scripts live inside in-world objects; per-avatar runtime permission grants (`llRequestPermissions` — take controls, animate, debit money) ([SL wiki](https://wiki.secondlife.com/wiki/LlRequestPermissions)); per-parcel script on/off; script-time accounting. The **"grey goo fence"**: after self-replicating object attacks, Linden rate-limited rez (replication) globally and across region boundaries — but kept legitimate self-replication for artificial-life builds; attackers adapted by replicating *below* the throttle threshold ([The Register, 2006](https://www.theregister.com/security/2006/11/24/second-life-plagued-by-grey-goo-attack/1362850); [Linden blog](https://lindenlab.wordpress.com/2006/10/09/goo-fence-error-message/); [LSL wiki: GreyGooFence](http://lslwiki.digiworldz.com/lslwiki/wakka.php?wakka=GreyGooFence)). Lesson: rate limits against adversaries are an arms race, not a wall.
- **Zachtronics (TIS-100 etc.)**: the save file IS the player's program, in a trivially readable plain-text format (`@node` blocks of assembly, `.asm` ≈ save format) — sharable, hand-editable, emulator-reimplementable ([TIS-100 Hacker's Guide save format](https://alandesmet.github.io/TIS-100-Hackers-Guide/save.html); [third-party emulator using the save format](https://github.com/Phlarx/tis)). Lesson: when the program-in-the-file is small, textual, and runs on a tiny fixed VM, the whole ecosystem (sharing, tooling, archival) comes free.

## WHAT SURVIVES CONTACT — recurring lessons

1. **Separate code from mutable state even when both live in the file.** The two healthiest architectures keep a hard wall: Factorio (code external, one serializable data table, no closures) and Screeps (code in modules, state in a 2MB JSON blob, IDs not references). The two famous casualties fused them: Smalltalk images (accumulated corruption, unversionable) and HyperCard stacks (script-splicing viruses, unforkable lineages). MOO fused them and paid in DB bloat and undeletable objects. If CS3.5 puts cultureway code in the save, store it as *source text in a distinct section*, with sim state referencing it — never closures-in-state.

2. **Data-only behavior gets you astonishingly far before you need a language.** DF raws and Minecraft's JSON (loot tables, advancements, predicates) encode huge behavioral variety declaratively — no sandbox, no budget, trivially diffable. The language is needed only for the residue. Corollary (Minecraft): if you under-design the language, one will *evolve anyway* out of your command/query surface, and it will be baroque (scoreboards-as-variables, `execute store`, macros) and become a compiler target rather than an authoring surface.

3. **Budgets must be architectural, not advisory — and interruption must be survivable.** MOO's ticks/seconds with abort-on-exhaustion and voluntary `suspend()`; Screeps' per-tick CPU + bucket + kill-mid-execution. Both force code into resumable, idempotent shapes. Any in-save cultureway interpreter needs a tick budget with defined semantics for "ran out mid-election-count."

4. **Determinism is a discipline you impose on guest code, not a property you hope for.** Factorio: guest state lives only in the serialized table; `on_load` is read-only; violations = desync. For CS3 (seeded deterministic sim, conservation proofs, headless regression matrix) this is the single most load-bearing precedent: cultureway code must be forbidden from ambient state, wall clocks, and un-seeded randomness, or the 230-scenario suite dies.

5. **Migration is the hard half; plan it before shipping v1.** Factorio ships per-mod ordered migration scripts + `on_configuration_changed` + save-side ID maps; Minecraft migrates its own data but abandons pack authors to `pack_format` churn; DF froze raws into saves and left "which edits break a live save?" formally unknown; MOO never solved core upgrades. The engine WILL change under saved code. Options proven in the wild: migrations-in-the-mod (Factorio), copy-and-freeze with version-gated updates (DF v50), format-range declarations (Minecraft 25w31a `min_format`/`max_format`).

6. **The trust model is identity + capability, and setuid is the sharp knife.** MOO's owner-permission verbs let untrusted users safely invoke privileged behavior — and LPC's mutable-reference escalation shows how capability leaks happen (hand a mutable ACL to a guest and it's theirs). Wizard bits, quota, and per-verb r/w/x are a complete small-world security model; its failure surface was social (governance), not mostly technical.

7. **Code in documents means viruses in documents.** merryxmas is the exact threat model for LLM-authored/shared cultureways: save files traded between players carrying self-propagating or subtly host-corrupting scripts, plus signature-evasion by trivial mutation. Grey-goo fence shows throttles alone lose to adaptive adversaries. Mitigations that existed: read-only Home stack protection (HyperCard, weak), real heap isolation (Screeps isolated-vm, strong), no-computation data formats (raws/JSON, strongest).

8. **A tiny fixed VM with a textual program format buys the whole ecosystem.** TIS-100's save-is-the-program works because the VM is small and frozen; third parties reimplemented it from the save format. MOO's DB survives 30+ years as a text dump. If the cultureway language is small, stable, and text-serialized in the save, sharing/diffing/LLM-authoring (CS4) come nearly free.

9. **If the world's rules are editable in-world, governance of the rules becomes gameplay.** LambdaMOO's petition/ballot machinery — implemented in the very softcode it governed, with residency requirements, vetting, and supermajorities — is the richest existing precedent for CS3's "local government with one remit," including its ending: the wizards took power back when the social layer outgrew the technical one.
