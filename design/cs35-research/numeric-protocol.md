## 1. SLICE ORDER (money-first validated, then the sequence)

**Money-first survives the coupling audit.** In the dataflow, money is a **sink, not a source**: needs/movement/clock feed money (patience ratio → tip, otMin → premium, dirt → tipMult) but money never multiplies a position, a need, or a timer. So slice 1 can quantize **at the point of mint** — float inputs stay float, the RESULT is canonically rounded to cents once — and every upstream subsystem is untouched. The two money→decision backflows are cheap: (a) affordability/threshold gates (`min(tip, wallet)`, `≥ $0.50`, dust `< 0.005`) become exact int compares (thresholds ×100 are whole cents); (b) the shelter sign-up **wallet sort with no tie-break** can acquire ties under cents — the tie-break (name or roster index) lands *inside* slice 1. Nothing forces a different first slice; money-first also front-loads the strongest tripwire (conservation as a theorem: `delta === 0`) that then referees every later slice. Confirmed.

## 2. THE RE-BASELINE PROTOCOL — the checklist an implementation fork follows

Per slice, in order; the payroll/one-wallet discipline generalized:

1. **Pin your own floor first.** On the tree you will land on (house rule — never PLAN's number): full suite green (247), baseline `--days 30 --seeds 16` (expect 0/16, median 12), growth `--buy chef,table` on **both** 8-seed blocks. Record all three in the PR.
2. **Develop with the shadow harness** (float reference beside int path, max-divergence logged). Divergence must match the slice's predicted bound (≤ half-cent for money; ≤ 1 ulp-of-Q for needs; unbounded-but-decision-sparse for movement). **Delete the shadow path before landing** — a float twin left in game.js is forked logic.
3. **Freeze the RNG stream.** The slice must consume the same draws in the same order (mint ints FROM the old draw, never add/remove a draw). `diff` of a draw-site count per frame is part of review.
4. **Suite, mechanisms first.** Full suite. Any scenario you relax or re-point gets **mutation-tested the four-goes way**: sever *all* paths to the asserted effect and watch it fail; a relaxed tolerance with no biting mutation is refused. Scenarios expected to *tighten* (money: `< 1e-6` → `=== 0` post-slice-1) are tightened in the same landing.
5. **Conservation soak.** 30-day run with `window._auditFund` on, every row `ok`; post-slice-1 the assertion is exact-zero. Any later slice that trips it has broken settlement ordering, not rounding — stop and attribute.
6. **The matrix floor, defined "unmoved":** baseline **0/16 exact** (gated); median eviction within ±1 of *your* step-1 measure; growth judged on **all 16 seeds** (both blocks — 8 is a coin, per CLAUDE.md), within one town per block with signs allowed in both directions; lifetime deltas small-% with **mixed signs** (the queue-pass noise signature: +3/−11/+1). Anything beyond: run the third seed block (the 0/48 idiom) before touching a single constant, then attribute with the narrow `_no*` hatch, never the broad one.
7. **Fingerprint LAST, with the diff-report.** Only after every other failure is understood ("a fingerprint re-pointed while the world is still wrong just freezes the wrongness"). Run the slice-0 diff script; every moved field must classify as **rounding-shaped** (sub-cent wallet deltas, ≤0.1px positions, unmoved serves/rage/catch) or carry a threshold-crossing trace explaining the behavior-shaped move (e.g. "seed 4242: SALTY's wallet crossed the $16 rent gate by 1 cent at day-2 settlement → slept at the shelter"). Write the receipt **in the scenario comment**, in the house voice, naming the slice. Both seeds. Measured on the landing tree; **a fingerprint is measured, never merged.**
8. **Save-migration proof** (see §3): load a pre-slice save; migrated `worldMoney()` equals the pre-migration rounded world total to the cent; every `roundtrip save/load` scenario green; the old-build refusal gate fires on the new envelope.
9. **Cross-engine receipt** — the point of the whole rewrite: run the fingerprint under a second JS engine/major version; the converted subsystem's fields must be bit-identical across engines. By slice 5 the full fingerprint is engine-independent; add that as a standing CI annotation.
10. **One slice per landing window.** If another branch re-baselined the fingerprint concurrently, re-measure on the merged tree (the 2026-08-20 five-pass precedent).

## 3. SAVE MIGRATION (per slice, `load()` flag idiom)

**Versioning:** a single staged counter `s._num` (0 = float era; 1 = cents; 2 = ticks; 3 = Q-needs; 4 = Q-pos), run stepwise in `load()` while `_num < CURRENT` — mirrors `migrateLegacy`'s crash-safe staging (converts in memory, persists on next `save()`). **Additionally bump `SAVE_VER` to 2 at slice 1**: a cents save read by an old build would inflate every balance ×100; the existing `_ver > SAVE_VER → "FROM A NEWER CRAB SHACK"` gate is exactly the refusal needed, and the import-refusal scenarios already cover the surface.

**Slice 1 (the one with a conservation obligation) — the remainder-assignment rule:**
1. Compute the world truth first: `W = Math.round(worldMoney() * 100)` on the loaded float state (after the existing `_oneWallet` reconcile, so tills are settled).
2. Convert every account by largest-remainder apportionment: floor each balance to cents, collect fractional parts, distribute the leftover `W − Σfloor` cents one each to the accounts with the largest fractions (deterministic tie-break: account name order). Result: `Σ accounts === W` — **rounding N wallets creates and destroys nothing**, by construction rather than by luck.
3. Ledger the dust: one `fundRow`-style line / dayLog entry, "MIGRATION: BALANCES SETTLED TO THE CENT" — auditable, in the house style of the laundromat refund toast.
4. Receipt for free: today a save/load cycle already breaks conservation (raw-float `coins`/`p.wallet` beside rounded-at-save `till`/`credit.bal`/`fund.bal` — the census bug). The migration scenario should assert the healed invariant and say so in its comment.
- Credit/debts (negative contributions) participate with the same rule; visitor purses in the save's stay ledger are already rounded ints — ×100 exact.

**Slice 2:** `tdgm = Math.round(tmin * 10)` (clamp 0..14399); `ferryT`, `restT`, `dayOpen` similarly; all 42 timers are transient (never saved) — no migration. `earnHist` timestamps rebuilt or dropped (it's a rolling display history; dropping is the honest migration).
**Slice 3:** needs `Math.round(v * 2^20)` clamped to [0, 2^20]; same for visitor `hu/th/di/bo/ti` (raw floats in today's envelope); `patience` likewise.
**Slice 4:** crabs are not position-persisted; visitors save rounded `x` → `x << 8`. Trivial.
Each migration is covered by the existing roundtrip scenario for its subsystem plus one new "old save (`_num` < k) migrates exactly" scenario per slice, in the `homeX era` / `legacy single-key` scenario lineage.

## 4. THE SEAM VERDICT

**The strangler does not hard-require rung 1 first — but slice 4 effectively does, and the owner's sequencing (rung 1 → rung 2) should stand with one licensed exception.** Grounding: draws are already fully runtime-gated (`window._headless`, ~0% of headless bill); the census shows 28/29 sines, `drawCrab`'s hypot, and camX are draw-only — so **money (slice 1) and clock (slice 2) touch the view only through display formatting** (`fmt$()`, minute rendering), which is itself seam work: introducing the formatter at every `"+$"+Math.round` site IS drawing the boundary those fields cross. The exception worth taking: **slice 1 can land before/parallel to the sim/view split with zero seam risk** — it de-risks the ladder early and its conservation theorem then referees the split itself. Rungs that must precede slice 4: the split flushes sim semantics hiding in view constants (lanes, queue slots, furniture x's — exactly the geometry slice 4 quantizes) and must first prove which of the two mist/shimmer-adjacent reads are sim (the census already caught `mistNow() > 0.6` in `visTick` — the split's golden state→draw-call seam tests are the systematic version of that catch). The RNG slice (5) also wants the split's inventory of browser-only consumers to be architectural fact, not census assertion, before routing them to a view stream.

## 5. RULING 7 AMENDMENT (proposed drop-in text)

> **Ruling 7a — the numeric boundary (amendment, effective the day slice 1 lands).** The triage gains a third lane. **Engine-shaped** CS3 changes that touch a *converted* subsystem (after slice 1: anything that mints, moves, or compares money; later: timers, needs, positions per the slice ledger below) may not merge textually — they are **TRANSLATED at the boundary**: dollars→cents through the one canonical rounding point, seconds→ticks (0.05s), needs→Q20, px→Q8, using the unit map maintained in `design/cs35-numeric-core.md`. The port PR names every converted unit it crossed. Validation moves from byte-equivalent to **behavior-equivalent, defined**: money effects reproduce the CS3 original **to the cent** after one canonical rounding; trajectory effects reproduce the original's *decisions and mechanism assertions* on the suite plus an unmoved 16-seed floor — never its floats. Engine-shaped changes to *unconverted* subsystems still merge straight through git; culture-shaped changes are still re-expressed, never hard-coded. A CS3 change that cannot express in the integer units — one that genuinely needs sub-cent money, sub-tick time, or a live transcendental — is a **NUMERIC-CORE bug, filed and prioritized as one** (the format-bug rule, applied to the number system), never worked around with a float island in game.js. The slice ledger (which subsystems are converted, which units, which rounding point) lives beside the unit map and is updated in the same landing as each slice.
